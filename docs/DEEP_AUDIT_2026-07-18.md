## 1. Correctness & Reliability — VERIFIED

### P1

- **Sub-second remainder discarded every tick (sum-of-floors) → systematic revenue under-charge on every session** — `firebase/functions/src/billing/tickConsultation.ts:197`
  - applyTick persists lastTickAt=Timestamp.fromMillis(billToMs) (line 197); the next tick measures elapsedMs=billToMs-lastTickAtMs and floors it (engine.ts:97-102), so the up-to-999ms remainder of each interval is dropped, never carried. Total billed = Σ floor(interval_i/1000) < floor(Σ interval_i/1000). In the common client-tick path billToMs==nowMs (gap<15s, frontier+15s≥nowMs) so the remainder is lost every heartbeat, and endConsultation's final tick (endConsultation.ts:100) just floors again with no reconciliation. The cumulative priorBilledSec/priorChargedPaise machinery makes paise exact against billed SECONDS but the seconds themselves leak.
  - _Fix:_ In applyTick, persist the next marker as lastTickAtMs + result.billedSeconds*1000 instead of billToMs. That value is always ≤ billToMs (billedSeconds≤floor((billToMs-lastTickAtMs)/1000)), so it preserves the frontier/anti-catch-up safety while accumulating the sub-second remainder into the following tick, making Σ billed seconds == floor(total present elapsed). Add a unit test running N ticks at 10,400ms spacing asserting total billed == floor(N*10.4).
- **pauseConsultation discards unbilled active time — free consultation via pause/resume abuse** — `firebase/functions/src/billing/pauseResume.ts:34`
  - pauseConsultation (31-40) writes status:'paused' with NO applyTick, and resumeConsultation resets lastTickAt to now (71), permanently discarding [old lastTickAt, pausedAt]; pausedAccumMs is never billed (applyTick always passes pausedSinceLastTickMs:0, tickConsultation.ts 105). Both are public callables the customer client invokes; a pause→resume loop under the 30s sweep grace (sweepSessions.ts 91) keeps lastTickAt fresh and never bills. billStaleActive (sweepSessions.ts 100-124) proves the correct pattern is applyTick-then-pause.
  - _Fix:_ In pauseConsultation load getGlobalConfig() and, inside the txn before writing status:'paused', run applyTick(tx, consultationId, config, nowMs, 'reconnecting', ticker) with ticker derived from the caller (as endConsultation.ts 97-99), matching billStaleActive so the trailing active span is billed to its clamped frontier and never discarded across a pause/resume cycle.
- **Payout amount is never validated positive — a negative-amount request INFLATES pendingPayout on processing (money leak)** — `firebase/functions/src/admin/actions.ts:104`
  - Guard `(p.amount ?? 0) > pending` (line 104) passes for a negative amount; line 119 then runs `increment(-(p.amount ?? 0))` = a positive credit to pendingPayout, and firestore.rules payouts create (lines 352-353) never constrains amount, with amount written client-side via SDK (wallet_tab.dart:41).
  - _Fix:_ At the top of applyPayoutDecision, before any state change: `if (!(typeof p.amount === 'number' && Number.isFinite(p.amount) && p.amount > 0)) failedPrecondition('INVALID_PAYOUT_AMOUNT');`. Also harden the payouts create rule to require `request.resource.data.amount is number && request.resource.data.amount > 0`.
- **AI keeps replying after wallet exhausted — 'paused' not terminal, no balance check** — `firebase/functions/src/ai/replyEngine.ts:67`
  - Line 67 only skips ['ended','cancelled','expired']; tickConsultation.ts line 203/208 flips an exhausted session to status:'paused', which passes the gate. There is no wallet/spendable read anywhere in replyEngine, and activateIfWaiting (line 681-694) only acts while status==='waiting', so a paused session is never re-billed — the full pipeline (chart, router LLM, reading LLM, guard, bubbles) runs and posts for free.
  - _Fix:_ Add 'paused' to the terminal-skip set for AI chats AND/OR read the customer wallet (wallet+bonus spendable) before generating and bail when it can't cover ~1 minute, mirroring the biller's exhaustion logic. Require explicit resume/recharge before an AI reply resumes a paused session.

## 2. Security — VERIFIED (46 findings, adversarially checked)

**Verdict.** The application is not launch-ready for real money in its current state. One P0 is disqualifying on its own: a live super-admin password (`Asktro@2026`) is permanently recoverable from git history, giving anyone with repo access full control of the admin plane. Beyond that, the dominant pattern is **broken authorization on money and privilege**: the admin tier model is enforced inconsistently (astrology/ops-tier admins can change commission splits, per-minute rates, block customers, mint discount codes, and broadcast to the whole base), astrologers can self-edit their own billing rates and trust fields via direct Firestore writes, and several money paths (first-recharge promo, store coupons, admin refunds/credits) fail check-then-act or idempotency and double-apply or over-grant. App Check is activated on the client but enforced on **zero** backend callables, so none of the abuse controls have teeth. A secondary cluster is **PII / special-category data exposure** (birth details, chat transcripts) to the lowest admin tier and to any astrologer who ever consulted once. Fix the P0, the P1s, and the App Check gap before touching a real launch.

- **AI keeps replying for free on a paused (balance-exhausted) chat** — `firebase/functions/src/ai/replyEngine.ts:67` — guard bails only on ended/cancelled/expired, not `paused`; the tick loop only bills `active`, so a scripted client gets unlimited free AI readings after wallet hits zero. **Fix:** bail on `paused` (or re-verify balance/re-activate before generating); gate the message-create rule on active/waiting status.

- **setUserStatus has no admin-tier gate** — `firebase/functions/src/admin/actions.ts:192` — any tier (incl. astrology) can set `accountStatus` to `blocked`/`deleted`, locking out paying users; `createConsultation` then rejects them. **Fix:** gate to `adminRole in {super,ops}`.

- **Store discount codes mintable by any admin tier** — `firebase/firestore.rules:303` — `storeCoupons` write gate is bare `isAdmin()`, unlike the super-only wallet `coupons`/`rechargePlans`; any tier can mint a 90%/free-ship code that checkout honors. **Fix:** gate to `isSuperAdmin()`.
- **Store coupon `usageLimit` overshoot race** — `firebase/functions/src/store/store.ts:111` — limit checked against confirmed-only `usedCount` at order creation but incremented only at payment confirmation, with no re-check; N unpaid orders all pass then all confirm. **Fix:** re-read and re-check the coupon inside `confirmStoreOrderPaid`'s transaction; add per-user redemption record.
- **Admin idempotency key regenerated on every retry** — `apps/admin/src/components/UsersActivityTable.tsx:145` — `opId: crypto.randomUUID()` minted inside the retryable handler, so a retry after a lost response re-applies `adjustWallet`/partial refund. **Fix:** mint `opId` once per intent (dialog open) and reuse on retry, or derive a stable server key.

- **Store-order webhook swallows confirm failures and amount mismatches** — `firebase/functions/src/store/store.ts:351` — mismatch/confirm-failure only logs and returns `true`, webhook 200s, Razorpay never retries and no dead-letter/alert (unlike the recharge path). - **Demoting/removing an admin does not revoke refresh tokens** — `firebase/functions/src/admin/admins.ts:115` — `setCustomUserClaims`/`disable` but no `revokeRefreshTokens`, and money callables read `adminRole` with no `checkRevoked`; a demoted super keeps a live super token for ~1h. **Fix:** `revokeRefreshTokens` on demote/remove and enforce token freshness on privileged callables.
